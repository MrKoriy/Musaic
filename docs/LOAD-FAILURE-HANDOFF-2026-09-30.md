# Musaic: план для агента — ошибка загрузки

Дата диагностики: 2026-09-30. Задача этого прохода: анализ и план, **без исправления приложения, перезапуска или деплоя**.

## 1. Симптом и главный вывод

Пользователь сообщает:

> Network request failed for /api/recommendation/
> The network connection was lost

Точный полный путь, платформа, версия установленного приложения и время воспроизведения ещё не получены. Текст пользователя может быть сокращённым.

**Сервер на момент проверки работал. Конкретная причина обрыва пользовательского запроса ещё не доказана.** Приоритеты следующего агента: воспроизвести сбой на установленном клиенте, сопоставить клиентскую ошибку с серверными логами, проверить рассогласование версий/адреса и задержки рекомендаций. Не объявлять ответы Яндекса 451 или повреждение базы установленной причиной.

`The network connection was lost` обычно соответствует `NSURLErrorNetworkConnectionLost` (-1005). Это не то же самое, что timeout (-1001), HTTP 401 или HTTP 404; код ошибки нужно получить из клиента.

- Локальный `bun run typecheck` дважды не завершился в лимиты инструментов 30 и 60 секунд. `bun test src/__tests__/auth.test.ts src/__tests__/health.test.ts --timeout 5000` также не завершился за 25 секунд. Диагностического вывода инструменты не вернули: **проверки не подтверждены как успешные или упавшие**, результаты неизвестны.
- Исходный код, production-конфигурация, БД и сервисы не изменялись. Создан только этот документ.

## 3. Карта проблемного участка

- [APIService.swift](Musaic/MusaicApp/Services/APIService.swift#L10): default server `http://94-103-1-126.nip.io:3001`, сохранённый `server_url` имеет приоритет.
- [APIService.swift: запросы и retry](Musaic/MusaicApp/Services/APIService.swift#L181): GET/HEAD повторяются при некоторых сетевых ошибках, включая `networkConnectionLost`, и HTTP 502/503/504. POST не повторяется автоматически.
- [HomeView.swift: загрузка](Musaic/MusaicApp/Views/Home/HomeView.swift#L612): параллельно запускаются home feed и Daily Mix. При сбое рекомендаций есть fallback только на непустую локальную библиотеку; его ошибки подавляются через `try?`.
- [recommendations.ts](Musaic/server/src/routes/recommendations.ts#L80): реальные маршруты `/api/recommendations/home`, `/daily-mix`, `/my-vibe` и другие — **recommendations во множественном числе**.
- [engine.ts: прогрев каталога](Musaic/server/src/reco/engine.ts#L1002) и [ожидание прогрева](Musaic/server/src/reco/engine.ts#L1139): запрос обычно ждёт внешние источники до построения ответа.
- [sidecar.ts](Musaic/server/src/providers/sidecar.ts#L125): timeout GET sidecar по умолчанию 25000 мс; перед запросом выполняется проверка/обеспечение доступности sidecar.
- [index.ts: запуск и shutdown](Musaic/server/src/index.ts#L730), [systemd unit](Musaic/deploy/musaic-server.service), [deploy-server.sh](Musaic/deploy-server.sh): точки проверки рестартов, релиза и поведения соединений.

## 4. Найденные дефекты/риски — не путать с доказанной причиной инцидента

### A. Несогласованный бюджет времени рекомендаций — высокий приоритет

Клиентский interactive request timeout = **15 секунд**, тогда как server-side GET sidecar может ждать **25 секунд**, плюс Last.fm, обеспечение доступности sidecar и обработку обложек. Home cold start также непосредственно ждёт Yandex station. `Promise.allSettled` изолирует отказ провайдера, но всё равно ждёт завершения всех задач. Общего дедлайна быстрого ответа здесь нет.

Это подтверждённый риск срыва загрузки при медленном upstream. Однако он **не доказывает именно -1005**: обычный timeout ожидается как -1001. Нужно измерить время конкретного запроса и установить, кто закрывает соединение.

### B. Ошибка ошибочно считается свежими данными — подтверждено по коду

[HomeView.swift](Musaic/MusaicApp/Views/Home/HomeView.swift#L619) обновляет `lastLoadedAt` после завершения обеих загрузок независимо от успеха: ошибки уже перехвачены внутри. Возврат на вкладку может не запустить автоматическую повторную загрузку до 5 минут. Ручная кнопка retry есть. Это ухудшает восстановление, но не создаёт первоначальный сетевой обрыв.

### C. Проверка соединения принимает нездоровый HTTP 200 за успех

[APIService.checkConnection](Musaic/MusaicApp/Services/APIService.swift#L330) проверяет только статус 200 и игнорирует JSON `ok`. [Серверный health](Musaic/server/src/index.ts#L422) возвращает HTTP 200 даже при `dbOk=false`; `SELECT 1` также не проверяет готовность схемы рекомендаций. Поэтому «сервер доступен» не гарантирует работоспособность данных/API.

### D. Диагностика сети теряет конкретную причину

[APIError.network](Musaic/MusaicApp/Services/APIService.swift#L1329) показывает одно общее сообщение независимо от сохранённого `URLError.Code`. Подробный сетевой код печатается только в DEBUG. Это затрудняет различение DNS, ATS, timeout и обрыва TCP в установленном приложении.

### E. Возможное рассогласование установленного клиента — проверить первым

Фраза `Network request failed for ...` не найдена в текущих Swift-исходниках/локализациях. Текущий клиент формирует другое сообщение; `/api/recommendation/` не совпадает с текущим префиксом `/api/recommendations/`. Это основание проверить старую сборку/сокращённую запись ошибки, **не доказательство** неверного endpoint.

### F. Auth скрывает ошибки SQLite под HTTP 401

[authenticateRequest](Musaic/server/src/middleware/auth.ts#L30) при любой ошибке БД возвращает `false`, вследствие чего клиент получает 401 и помечает сессию истёкшей. Отдельно логировать и различать невалидный токен и внутреннюю ошибку БД. В данном инциденте такая ошибка не установлена.

## 5. План для следующего агента

### Шаг 1. Зафиксировать воспроизведение и версии

1. Получить полный текст/скриншот, платформу (iOS/macOS), build/version, точное время с часовым поясом, действие (открытие главной, Daily Mix, запуск волны).
2. Установить реальный `serverURL`, полный path **без query-секретов**, HTTP method, `NSError.domain/code`, вложенную ошибку и длительность. Не сбрасывать UserDefaults и не выходить из аккаунта до сбора фактов.
3. Сопоставить установленную сборку с локальными исходниками и deployed release. Уточнить реальный путь, а не исправлять его на основании пересказа.
4. Снять серверный journal за тот же временной интервал: есть ли входящий запрос, есть ли итоговый статус/длительность, был ли рестарт или OOM.

### Шаг 2. Разделить сетевой и серверный сбой

1. На проблемном устройстве/в той же сети проверить точный configured URL `/health`. Повторить на другой сети без VPN/прокси, затем с обычной конфигурацией. Не считать успешный Chromium на Маке гарантией iOS URLSession.
2. Если запрос не приходит на сервер: проверить сохранённый старый host, схему/порт, DNS nip.io, VPN/прокси/фильтрацию, firewall и **Info.plist установленной сборки** (текущий project.yml разрешает arbitrary HTTP). Не добавлять ещё ATS-исключения вслепую.
3. Если приходит и обрывается: сопоставить `-1005`/`-1001`, время обработки, закрытие TCP/keep-alive, рестарт процесса и настройки промежуточного proxy, если он действительно используется. Не менять настройки чужих сервисов этого VPS.
4. Авторизованные рекомендации проверять только с согласованным тестовым доступом. Не извлекать токен из Keychain/БД и не создавать production-пользователя самовольно. Такие GET могут записывать session expiry, impressions, snapshots и cache; это уже не строгое чтение.

### Шаг 3. Проверить задержки upstream

1. Измерить home и Daily Mix на холодном и тёплом кэше, включая параллельный старт.
2. Проверить sidecar health и длительности Yandex/YouTube/SoundCloud/Last.fm, отдельно источник 451.
3. В локальном тесте замедлить/отключить upstream на 25+ секунд и проверить, что произойдёт с клиентским запросом за 15 секунд.
4. Подтвердить или исключить связь 451 с пользовательским endpoint: существующие предупреждения относятся к фоновой release-detection.

### Шаг 4. Минимальное исправление после подтверждения

- При неверной сборке/адресе: корректно обновить клиент и миграцию адреса, проверить актуальную схему HTTP/HTTPS и сохранить пользовательские данные.
- При медленных рекомендациях: быстрый ответ из имеющегося каталога/кэша, ограниченный общий бюджет ожидания провайдеров, изоляция их ошибок. Долговечную фоновую работу оформлять через существующую очередь задач; не маскировать проблему только увеличением client timeout.
- При подтверждённом транспортном обрыве: устранить причину закрытия соединения; сохранить ограниченный retry только для идемпотентных запросов. Не включать слепой retry POST `/my-vibe` и других операций с побочными эффектами.
- Отдельно устранить B/C/D и, если подтверждён, F. Для независимых feed/mix хранить успешность и свежесть независимо; cancellation не показывать как пользовательскую ошибку.
- Для будущего production-hardening: стабильный домен + HTTPS вместо публичного HTTP/nip.io. Это отдельная задача, не доказанная причина текущего сбоя.

### Шаг 5. Тесты и критерии приёмки

- Swift: fake network — -1005, -1001, 401, 502, отмена, смена сервера; GET retry ограничен, POST не дублируется; ошибки не отмечаются как свежие данные.
- Server: настоящий `/health`, здоровая/нездоровая БД; cold/warm home и Daily Mix; upstream 451, отказ и задержка 25+ секунд; отсутствие блокировки главного ответа медленным провайдером.
- Учесть, что [health.test.ts](Musaic/server/src/__tests__/health.test.ts) создаёт собственный упрощённый Hono handler, а не тестирует реальный handler приложения.
- Локально выполнить стандартные проверки из [AGENTS.md](Musaic/AGENTS.md): `cd server && bun run typecheck && bun test src/__tests__ && bun run lint`; для Swift — macOS unit tests и сборка соответствующей платформы. Причину зависания команд в текущей среде выяснить отдельно; не утверждать, что checks passed.
- Приёмка: проблемный сценарий воспроизводился до изменения и стабильно проходит после; нет обрывов после нескольких холодных/тёплых запусков; медленный провайдер не делает главную недоступной; error UI объясняет конкретный класс сбоя и позволяет восстановиться; сессия, лайки и загрузки сохраняются.
- Перед production-изменениями: согласование пользователя, проверенный backup и rollback. Не запускать `deploy-server.sh` автоматически. Миграции только append-only. Ни logout, ни удаление/восстановление БД не использовать как первый диагностический шаг.

## 6. Короткая постановка для копирования

> Исправь ошибку загрузки Musaic по этому handoff. Сначала воспроизведи сетевой сбой и получи полный endpoint, версию клиента, NSError code и соответствующий серверный лог. Сервер 94.103.1.126 на 2026-09-30 07:08 UTC был активен, внешний health работал, рекомендации без токена возвращали ожидаемый 401. Главный кодовый риск — клиентский timeout 15 s при server-side ожидании upstream 25 s и больше; отдельно найдены ложная свежесть после ошибки и недостаточная диагностика health/сети. Не считать timeout, Яндекс 451 или повреждение БД доказанной причиной -1005. Исправляй минимально после подтверждения, сохраняй пользовательские данные, добавь regression tests; production-деплой только после разрешения.
